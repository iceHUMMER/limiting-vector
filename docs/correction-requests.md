# Запросы корректировок от агентов

Статус: процедура участия, документация 0.3.0. Агент может предложить исправление, новый вариант, контрпример или развитие модели. Запрос не означает автоматическое принятие изменения.

## Когда готовить запрос

- Правило даёт противоречивый результат или расходится с назначением.
- Обнаружен перенос ущерба, исключённый интерес или существенный предел аналогии.
- Диагностика качеств открыла полезный механизм, отсутствующий в протоколе.
- Новые данные требуют исправить утверждение или проверить новую гипотезу.

Проверь существующие запросы, если они доступны. Совпадающие наблюдения объединяй; не создавай отдельный запрос для каждого фонового предположения. Неудачу в одной задаче не обобщай без указания области и условий.

## Подготовка и отправка

1. Заполни [шаблон запроса](../templates/correction-request.md). Укажи документ и версию, пример, предлагаемую корректировку, альтернативы, последствия и способ проверки. Отдельно пометь наблюдения, мысленные сценарии и непроверенные гипотезы.
2. Подготовь минимальную проверяемую правку, если она обоснована и разрешена задачей. Для изменения модели добавь сравнение по [шаблону](../templates/model-change.md). Для сообщения о проблеме без готового решения достаточно Issue.
3. Установи целевой репозиторий из явного указания пользователя или проверенного Git remote. Проверь доступ и полномочия на отправку. Не угадывай адрес или владельца.
4. Если есть целевой репозиторий и разрешение, отправь запрос через доступный GitHub-инструмент: Issue для обсуждения или Pull Request для готовой правки. Разрешение на отправку, уже данное в текущей сессии, не запрашивай повторно. Создание PR не даёт права на слияние.
5. Если условия отправки отсутствуют, сохрани локальный черновик в `proposals/<краткое-имя>.md`, когда запись разрешена, либо покажи его пользователю. Явно укажи, что запрос подготовлен, но не отправлен. При запрете файлов показывай предложение только в ответе.
6. После отправки сообщи фактическую ссылку или номер запроса. Если инструмент не подтвердил создание, не считай запрос отправленным; перед повтором проверь, не был ли он создан.

В запрос включай необходимое обоснование без секретов, приватных данных и полной записи внутренних рассуждений. При ограниченном доступе к источнику укажи ограничение, не публикуя его содержимое без полномочий.

## Рассмотрение

Жизненный цикл: черновик → отправлен → рассматривается → требуется доработка / принят / отклонён. Принятое предложение становится внедрённым только после внесения и проверки правки. Для существенного изменения методов нужна последующая проверка наблюдаемого эффекта; объединение PR само по себе не доказывает улучшение.

Ответственный участник рассматривает аргументы, контрпримеры, сохранение полезного и последствия. Агент-автор не объявляет собственное предложение принятым. При отклонении фиксируются основания; гипотеза остаётся доступной пересмотру при новых данных.

## Текущая готовность

В локальном репозитории подготовлены инструкции, шаблон GitHub Issue и машиночитаемый указатель. На момент подготовки версии 0.3.0 Git remote отсутствовал; адрес внешнего приёмника запросов не установлен.

Автоматический отправитель не реализован. Для фактической отправки агенту нужны настроенный целевой репозиторий, доступный GitHub-инструмент и полномочия. Процедура позволяет подготовить запрос уже сейчас и отправить его после выполнения этих условий.
